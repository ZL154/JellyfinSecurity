# Jellyfin Security v2.5.0 — Design Spec

**Status:** Approved for implementation planning
**Date:** 2026-05-28
**Target version:** v2.5.0 (single release, smoke-tested on home server before catalog)

## Overview

v2.5.0 is the largest feature release since v2.0. It adds an admin-facing **security
metrics dashboard** with a real computed **security posture score**, two opt-in
**security-hardening** controls (require-TOTP-to-disable-own-2FA, multi-level step-up
auth for admin actions), **config export/import**, and **8-language i18n**.

Two capabilities discussed during brainstorming already exist in the codebase and are
**surfaced, not rebuilt**: the audit-log hash chain (already computed + verified by
`DiagnosticsService.VerifyAuditChain`) and the webhook/notification system (ntfy /
Gotify / signed generic webhook / email — already in `PluginConfiguration` +
`NotificationService`).

### Goals

- Give admins at-a-glance visibility into their security posture and the data the
  plugin already collects (audit events, bans, enrollment, sessions, audit integrity).
- Close two real hardening gaps (`DisableTotp()` currently re-auths nothing; sensitive
  admin actions have no step-up requirement) — both opt-in so upgrades don't surprise
  existing admins.
- Let admins back up / migrate their setup.
- Reach non-English users with the same 8-language support as AchievementBadges.

### Non-goals

- Rebuilding the audit hash chain or the webhook system (already exist).
- SAML / SCIM / push-2FA / geo-fencing (future releases; out of scope here).
- Per-user-secret migration as the *default* export mode (opt-in only, see §3).

## Scope decisions (locked during brainstorming)

| Decision | Choice |
|---|---|
| Release slicing | Single v2.5.0, build everything, smoke-test on home server, then ship |
| Build order | hardening → score+dashboard → export/import → i18n (i18n last, after UIs settle) |
| Hardening toggle defaults | Both OFF on upgrade, with a "Recommended" badge + one-line explainer |
| Step-up auth | Multi-level enum, not binary: Off / Destructive / AllConfigChanges / Everything |
| Export scope | Both modes: config-only default + opt-in passphrase-encrypted full backup |
| i18n resolution | Mirror AchievementBadges: per-user pref → admin DefaultLanguage → `en` |
| Score recalculation | On-demand live (computation is <10ms) + daily snapshot for trend history |
| Dashboard charts | Hand-rolled SVG (no client-side chart-library dependency) |

## 1. Security hardening

### 1a. Require-TOTP-to-disable-own-2FA

**Config:** `bool RequireTwoFactorToDisable` (default `false`). Surfaced in admin UI with a
"Recommended" badge and explainer: *"Require a fresh authenticator code before a user can
turn off their own 2FA. Stops an attacker who has the password from disabling the second
factor."*

**Behavior:** `POST /TwoFactorAuth/Setup/Disable` (currently `[Authorize]`, wipes 2FA with
no re-auth) gains a guard. When `RequireTwoFactorToDisable` is on:
- Request must include a fresh TOTP or recovery code.
- Verify it (reuse existing TOTP verification + replay protection) before the mutate/wipe.
- Missing/invalid → `403` with the `twoFactorRequired:true` body marker so the existing
  challenge UI re-prompts.

Candidate (note, not committing in v2.5.0 unless trivial): also gate recovery-code
regeneration the same way. Decide during implementation; default to disable-only.

### 1b. Step-up auth (multi-level)

**Config:** `StepUpLevel` enum — `Off=0`, `Destructive=1`, `AllConfigChanges=2`,
`Everything=3` (default `Off`). Admin UI shows it as a dropdown with a "Recommended:
Destructive" hint.

**Action classification:**
- **Destructive (level ≥ 1):** disable enforcement globally; reset or disable *another*
  user's 2FA; config export with secrets; unban-all.
- **AllConfigChanges (level ≥ 2):** + any settings save, OIDC provider add/edit/delete,
  allowlist/CIDR edits, single IP unban, config import.
- **Everything (level ≥ 3):** + viewing the audit log.

**Mechanism:** A short-lived "step-up verified" token per admin, ~5 min TTL, stored in the
existing `ChallengeStore`. Gated endpoints check `StepUpLevel`; if the action is in-scope
and no valid step-up token is present, return a challenge-required response (`403` +
marker). The admin UI prompts for a TOTP code, exchanges it for a step-up token via a new
`POST /TwoFactorAuth/StepUp/Verify`, then retries the original action. Token scoped to the
admin's user id; cleared on logout.

**Tests:** classification table (each action → required level), token TTL/expiry, and that
`Off` is a pure pass-through (no behavior change for admins who don't opt in).

## 2. Security score + dashboard

### 2a. Security score engine

New service `SecurityScoreService`. Computes a 0-100 score live (no caching — full
computation is <10ms) and returns a structured breakdown for the UI.

**Weighted factors (sum to 100):**

| Factor | Points | Source |
|---|---|---|
| 2FA coverage (% of users enrolled) | 30 (scaled by %) | user store |
| All admins protected | 20 (binary) | user store + Jellyfin admin role |
| Enforcement mode | Everyone 15 / Admins-only 8 / Optional 0 | config |
| Audit chain verified (no anomalies) | 10 / 0 | `DiagnosticsService.VerifyAuditChain` |
| IP banning enabled | 8 | config |
| Impossible-travel enabled | 7 | config |
| HIBP breach check enabled | 5 | config |
| No breach/lockout events in last 7 days | 5 | audit scan (7-day window) |

Returns: total score, letter grade (A/B+/…), per-factor `{label, earned, possible, status}`,
and a "next actions" list (gaps sorted by point value) for the actionable nudge.

### 2b. Daily score snapshot

Piggyback the existing audit-flush background timer. Once per day, compute the score and
append `{date, score}` to a capped `score-history.json` (max 365 entries). Powers the trend
arrow ("▲ up N pts") and 30-day score sparkline. Tiny data footprint.

### 2c. Overview endpoint

`GET /TwoFactorAuth/Dashboard/Overview` (admin-only). Returns:
- Current score + breakdown + next-actions
- KPIs: enrolled count / total, active sessions (+ user/device counts), banned IP count,
  audit integrity (verified bool + entry count + anomaly count)
- Enrollment by role: admins enrolled/total, standard users enrolled/total, not-yet-enrolled
  username list
- Auth-event time series (success vs failed, bucketed) from the audit log, honoring a
  range param (`24h` / `7d` / `30d`)
- Ban list from `IpBanService` (IP, geo/ASN if GeoIP DB present, trigger, failure count,
  expiry)
- Score history from the daily snapshot

Computes live; reads audit log + `IpBanService` + session manager + user store. No new
persistent state beyond the score snapshot.

### 2d. Dashboard UI

Rendered in `admin.html` (new "Overview" section/tab) per the approved v2 mockup:
posture banner with score ring + grade, score-breakdown panel with per-factor bars + the
"+N pts available" nudge, KPI strip with trend sparklines, auth-activity area chart with
30d/7d/24h toggle, enrollment-by-role bars + not-enrolled chips, rich ban table (geo, ASN,
trigger badge, attempt-pattern sparkline, inline unban).

**Charts:** hand-rolled inline SVG (area chart, sparklines, donut/ring via conic-gradient).
No client-side chart library — keeps the plugin's web surface dependency-free.

## 3. Config export / import

### 3a. Export

`GET /TwoFactorAuth/Config/Export?includeSecrets={bool}` (admin). Step-up gating matches
the §1b classification: `includeSecrets=true` is **Destructive** (gated at level ≥ 1);
config-only export is an admin read of non-secret settings and is **not** step-up-gated
(the admin is already authenticated). Import (§3b) is a config change → **AllConfigChanges**
(gated at level ≥ 2).

- **Config-only (default, `includeSecrets=false`):** enforcement scope + all toggles,
  LAN/trusted-proxy CIDRs, IP-ban + impossible-travel settings, OIDC provider configs
  **with client secrets excluded**, SMTP config **with password excluded**, webhook
  configs **with secrets excluded**, score config, `DefaultLanguage`. Import re-creates
  settings; users re-enroll; admin re-enters secrets.
- **Full (`includeSecrets=true`):** everything above **plus** per-user 2FA data (encrypted
  TOTP secrets, recovery-code hashes, device/trust tokens) **plus** the excluded secrets.
  The entire payload is wrapped: `PBKDF2-SHA256(passphrase, salt)` → `AES-256-GCM`. Admin
  supplies the passphrase at export and import.

### 3b. Import

`POST /TwoFactorAuth/Config/Import` (admin; step-up-gated). Accepts the JSON (+ passphrase
if encrypted). Validates the versioned envelope, applies settings (and per-user data if
present + decryptable).

**Format envelope:** `{ formatVersion: int, exportedAt: ISO-8601, pluginVersion: string,
encrypted: bool, payload: <object | base64-ciphertext> }`. Reject malformed; warn (don't
hard-fail) on `pluginVersion` mismatch; hard-fail on unknown `formatVersion`.

## 4. i18n (8 languages)

Mirrors the AchievementBadges architecture exactly.

- **Languages:** de, en, es, fr, it, ja, pt, zh.
- **Files:** `Pages/translations/{lang}.json` (embedded resources). `en.json` is the
  source-of-truth key set.
- **Endpoint:** `GET /TwoFactorAuth/translations/{lang}` serves the JSON (sanitize `lang`
  to `[a-z-]`, fall back to `en` on miss).
- **Client:** `tr(key, fallback)` helper added to `inject.js`, `setup.html`,
  `challenge.html`, `admin.html`. All user-visible strings keyed.
- **Resolution:** per-user `Language` preference → admin `DefaultLanguage` config → `en`.
- **New config:** `string DefaultLanguage` (default `"en"`); per-user `Language` stored in
  user 2FA data + a small preference endpoint (mirror AB's user-preferences pattern).
- **Translation process:** machine-translate the 7 non-English files from `en.json`, then
  **human-review the security-critical strings** (challenge/verify/disable confirmations,
  warnings, error messages) — a mistranslation of "Disable 2FA" vs "Disable account" is a
  safety issue, not just a polish issue.

## 5. Surface existing systems (no rebuild)

- **Audit hash chain:** already computed in `UserTwoFactorStore.AddAuditEntryAsync` and
  verified by `DiagnosticsService.VerifyAuditChain` (exposed via `RunDiagnostics()`). The
  dashboard's "audit integrity" KPI calls the existing verifier — **no crypto changes.**
- **Webhooks/notifications:** ntfy / Gotify / signed generic webhook / email already exist.
  Optionally widen which events fire them (e.g., score drop, new ban, 2FA disabled) — low
  priority, may defer to a point release.

## Cross-cutting: test strategy

Stryker baseline (run 2026-05-28): mutation score 7.31% overall, but that's dominated by
4496 never-covered mutants concentrated in integration-heavy files (controllers, services).
Covered code kills ~64% of mutants; 208 survived (weak assertions).

For v2.5.0:
- **All new services ship with xUnit tests** — `SecurityScoreService` (factor math + grade
  thresholds + edge cases like 0 users), step-up token TTL/scope, export/import round-trip
  + encryption + version validation, i18n resolution + `lang` sanitization.
- **Opportunistic coverage** on the 0-coverage files we touch: `AuthenticationEventHandler`
  (step-up hooks), `DiagnosticsService` (`VerifyAuditChain` for the dashboard),
  `NotificationService` (if widening events).
- **Warm-up win:** strengthen `OidcProviderPresets` tests (66 survived mutants — tests
  check presets exist but don't assert field values).
- **Re-run Stryker** after implementation to confirm new code is well-covered (target: new
  files at high kill rate, even if the overall number stays low due to legacy controllers).

## New config fields (summary)

`RequireTwoFactorToDisable` (bool, false), `StepUpLevel` (enum, Off), `DefaultLanguage`
(string, "en"). Per-user: `Language` (string, default empty = "use admin default").

## New endpoints (summary)

- `POST /TwoFactorAuth/StepUp/Verify`
- `GET /TwoFactorAuth/Dashboard/Overview`
- `GET /TwoFactorAuth/Config/Export`
- `POST /TwoFactorAuth/Config/Import`
- `GET /TwoFactorAuth/translations/{lang}`
- (+ per-user language preference get/set, mirroring AB)

## Release

Single **v2.5.0**. Build in the dependency order above, smoke-test the full build on the
home server (`<home-server>`, docker `jellyfin`) across all login methods +
the new dashboard/export/i18n surfaces, then tag + catalog.
